Services and infrastructure

Databases, cache, search, mail and storage run beside your applications as native processes, and the infrastructure canvas wires them in.

The infrastructure canvas

An application's Infrastructure tab draws its services as a canvas: PHP, its databases, cache, mail, search, storage and processes, joined to the application.

Add a database and Phun asks which engine: MySQL, MariaDB, PostgreSQL, SQLite or MongoDB. Add MySQL (or whichever you pick) installs and starts it, writes the settings and creates the database; Install only leaves your settings alone. An application can use more than one database; each gets a card with the connection name to use.

Phun only offers the services an application can use, and writes them where its framework reads them:

  • Laravel: .env.
  • Symfony: .env.local, one DSN each, such as DATABASE_URL and MAILER_DSN.
  • CodeIgniter: its own .env settings for databases, Redis, Memcached and mail.
  • WordPress: wp-config.php, MySQL or MariaDB, and Redis for the Redis Object Cache plugin.

An HTML application gets no services. One Phun cannot wire yet, such as CakePHP, Slim or plain PHP, is told so instead of being offered settings it would ignore.

A shared service's card on the canvas offers what belongs to the application: its logs, the database browser, Global Config and Remove. Starting, stopping, ports and versions live on the Services page, since they affect every application.

Processes

For Laravel, the canvas runs queue workers (as many as you need, each with its own queues and log), the scheduler and Reverb. Symfony gets Messenger workers. WordPress, CodeIgniter, Drupal and Magento get scheduled tasks, which run the application's own cron command every minute.

phun queue enable blog
phun schedule enable blog
phun messenger enable shop

The Services page

Services, on the Overview, lists every service Phun can run, installed or not, with Install or Update in its row. They run natively, started with Phun: no Docker, no virtual machine.

  • Databases: MySQL, MariaDB, PostgreSQL and MongoDB.
  • Cache: Redis and Memcached.
  • Search: Meilisearch, Typesense and OpenSearch.
  • Live updates: Mercure.
phun services
phun service install redis <version>
phun service set-port mysql 3307

Mail, storage and databases

Caught mail and S3-compatible storage have their own page, Mail and storage, and the database browser and schema canvas are in Databases.

Developer tools

Composer, Node.js, Bun, the Laravel installer, WP-CLI and Chrome for Testing install when you need them, without a system package manager.

phun tools
phun install tool node  # the latest Node.js LTS

Node.js versions

Install as many Node.js versions as your projects need, from the official nodejs.org builds, each checked against its published SHA-256. Name a major, an exact version, lts, an LTS line such as lts/iron, or latest. The Node.js versions card under Developer tools lists them and installs more.

phun install node 20
phun install node lts/jod
phun list node
phun uninstall node v20.11.1

Phun's node, npm and npx pick a version for the folder you run them in, and so do the Vite and npm workers Phun starts for an application. The first of these wins:

  • The application's own version, set in its Settings › Node.js or with phun use blog node 20.
  • The project's files: the nearest .nvmrc, then .node-version, then package.json's engines.node, looking upward from the folder.
  • The default, set on the card or with phun use node 22.
  • The newest installed version.

The highest installed version that matches is used. A version an application, .nvmrc or .node-version asks for that is not installed stops with the command to install it; an engines.node range nothing matches only warns. Settings › Node.js shows only for applications with a package.json. phun use blog node auto clears an application's version.

phun use node 22  # the default
phun use blog node 20  # just blog.test
phun use blog node auto # back to blog's .nvmrc or the default

With nvm

Phun's bin folder comes before nvm's on your PATH, so Phun steps aside instead of fighting it. When nvm (or fnm) has a version active in your shell, after nvm use or from nvm's default alias, Phun's node, npm and npx run that version. Two settings change this:

  • phun set node manager phun: always run Phun's versions, even with nvm loaded.
  • phun set node manager external: take node, npm and npx out of Phun's bin folder altogether and leave them to nvm. Phun keeps its versions for its own use.
phun set node manager auto  # the default: step aside when nvm is active

On Windows, Phun's bin folder holds a copy of the default version and that is the one that runs: the per-application and project-file choices apply on macOS and Linux.
