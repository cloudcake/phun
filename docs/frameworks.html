Frameworks

Phun knows each framework: its workers, its console, where it reads its settings, and the libraries it uses.

Your stack, recognised

Every application shows its framework and the libraries it uses, with their versions: Laravel, Livewire, Filament, Vue, React, Svelte, Alpine.js, Inertia, Tailwind and Vite, plus Symfony, CodeIgniter, CakePHP, Slim, Drupal, Magento, Yii and WordPress. Versions come from what is installed, else from the version your project asks for.

Laravel

  • Queue workers, as many as you need, each with its own name, queues, connection, settings and log.
  • The scheduler and Reverb, each with its own log.
  • Artisan and Tinker in the dock; see Terminals and the dock.
  • Setup checks with a one-click fix: an APP_URL that is not the address Phun serves the application on, an empty APP_KEY, a missing public storage link, and a cache, session, queue or database pointing at a Phun service that is stopped or not installed.
phun queue enable blog --processes 2
phun schedule enable blog
phun reverb enable blog
phun artisan blog migrate  # key-generate, storage-link, migrate or optimize-clear
phun filament optimize blog

Symfony

Phun writes a Symfony application's settings to .env.local and leaves .env for the defaults you commit; services added on the canvas write one DSN each. bin/console sits where Artisan does, with the command list and forms. Messenger workers consume the transports you choose (async by default) with process, time, memory and message limits, and Symfony's own log has its tab.

phun new symfony shop --webapp
phun messenger enable shop
phun console shop cache:clear

WordPress

Create a WordPress site from Create, or phun new wordpress. Services are written into wp-config.php: MySQL or MariaDB, and Redis for the Redis Object Cache plugin. Turn on one-click admin sign-in under the application's Settings › HTTPS, or from the terminal:

phun wordpress auto-login site on
phun wordpress login-url site  # a one-time admin sign-in link
phun wordpress users site

CodeIgniter, Drupal, Magento and more

CodeIgniter gets its databases, Redis, Memcached and mail in its own .env settings. WordPress, CodeIgniter (with codeigniter4/tasks), Drupal (with Drush) and Magento get scheduled tasks from Infrastructure › Processes, which run the application's own cron command every minute, with its output in the application's logs and a notification when a run fails.

HTML applications

Create › HTML app makes a folder with an index.html, served as it is, from a plain page or a single-page app with a few client-side routes. Phun answers any path that is not a file with index.html, so reloading /about still works. No PHP version has to be installed and no PHP process starts; a request that needs PHP, such as a .php script or a POST, still goes to PHP.

The environment

An application's Settings › Environment edits its .env; Phun hides values until you reveal them. Profiles are the .env.<name> files beside it (.env.testing, .env.example and so on): compare one with the current .env key by key and use it in its place, keeping the old one as .env.backup and clearing Laravel's cached config. Save current as writes a new profile.

phun env blog MAIL_FROM_ADDRESS=hello@blog.test
phun dotenv blog

JavaScript

phun js-install blog installs an application's JavaScript dependencies with its own package manager, and phun npm enable blog dev keeps an npm script running beside it.
